Ниже нормальное ТЗ под **MVP Telegram-бота для публичного чата**, без сказок про “полностью не пускать в паблик”, потому что в паблике Telegram так не работает. Но сделать так, чтобы без подписок человек **не мог нормально писать, а его сообщения сносились, он ловил мут и бот не срал уведомлениями каждую секунду** - это вполне рабочая хуйня.

# ТЗ на MVP Telegram-бота контроля подписки для публичного чата

## 1. Цель продукта

Сделать Telegram-бота, который для **публичного чата**:

1. Проверяет, подписан ли участник на обязательные чаты / каналы.
2. Не даёт участнику полноценно пользоваться основным чатом, пока условия не выполнены.
3. Удаляет сообщения нарушителя.
4. Выдаёт мут за спам-попытки писать без выполнения условий.
5. Не шлёт дублирующиеся уведомления.
6. Удаляет сервисные сообщения спустя заданное время.
7. Используется именно для **монетизации публичных сообществ**, а не для приватных join-request схем.

---

## 2. Бизнес-суть

Система нужна для монетизации пабликов через принудительный funnel:

* пользователь заходит в основной публичный чат;
* чтобы писать в нём, он обязан подписаться на заданные каналы / чаты;
* пока условия не выполнены, бот ограничивает доступ к общению;
* таким образом владелец паблика продаёт размещение / подписки / трафик партнёрам или своим сеткам.

---

## 3. Важное ограничение Telegram

### 3.1. Что можно

В публичном чате можно:

* удалять сообщения неподписанных пользователей;
* ограничивать право писать;
* выдавать мут;
* показывать уведомление с условиями и кнопками;
* повторно проверять подписку по кнопке или по действию пользователя.

### 3.2. Что нельзя

В **публичный чат** нельзя “вообще не пускать” пользователя на уровне входа так же жёстко, как в приватном invite-only сценарии.

### 3.3. Реальная модель для MVP

Не “не пускать физически”, а:

* **разрешить зайти в чат**,
* но **не давать писать**, пока не подписался,
* любые попытки обойти это удалять,
* при повторных попытках мутить.

То есть по факту для юзера чат до выполнения условий бесполезен. Этого достаточно для монетизации, и это уже не инфантильные фантазии про магию API.

---

## 4. Роли

### 4.1. Администратор

Может:

* подключать основной чат;
* задавать список обязательных каналов / чатов;
* настраивать TTL удаления уведомлений;
* настраивать политику мута;
* включать / выключать дедуп уведомлений;
* смотреть базовую статистику.

### 4.2. Пользователь

Может:

* зайти в публичный чат;
* получить уведомление с условиями;
* подписаться на обязательные каналы / чаты;
* нажать кнопку проверки;
* после выполнения условий получить право писать.

### 4.3. Бот

Должен:

* быть админом в основном чате;
* быть добавлен в обязательные каналы / чаты, чтобы проверять membership;
* иметь права:

  * delete messages
  * restrict members
  * ban/unban, если используется жёсткий режим
  * invite links не обязательны для MVP

---

## 5. Основной сценарий работы

## 5.1. Вход нового участника

1. Пользователь вступает в основной публичный чат.
2. Бот проверяет подписку на обязательные цели.
3. Если условия выполнены:

   * ничего не ограничивает;
   * пользователь может писать.
4. Если условия не выполнены:

   * бот ограничивает право отправки сообщений;
   * отправляет уведомление с инструкцией;
   * показывает кнопки на обязательные каналы / чаты;
   * показывает кнопку **“Проверить подписку”**.

## 5.2. Попытка писать без подписки

1. Если пользователь всё ещё не подписан и пытается писать:

   * сообщение удаляется;
   * фиксируется нарушение;
   * при необходимости выдаётся уведомление, но без дублей;
   * при превышении лимита попыток пользователь получает мут.

## 5.3. Повторная проверка

1. Пользователь нажимает кнопку **“Проверить подписку”**.
2. Бот заново валидирует статус.
3. Если всё ок:

   * снимает ограничения;
   * удаляет сервисное сообщение;
   * optionally отправляет короткое подтверждение.
4. Если нет:

   * оставляет ограничения;
   * обновляет статус / уведомление без спама.

## 5.4. Отписка после получения доступа

Для MVP желательно поддержать повторную проверку не только при входе, но и позже:

* либо при нажатии кнопки,
* либо при первой попытке писать после истечения кеша проверки.

Если пользователь получил доступ, а потом отписался:

* при очередной проверке бот снова ограничивает его.

## 6. Функциональные требования

# 6.1. Управление обязательными подписками

Система должна позволять для каждого основного чата задать список обязательных целей:

* Telegram-каналы
* Telegram-группы / супергруппы

### Требования

* MVP: логика **“подписан на всё из списка”**
* каждая цель хранится отдельно
* можно включать / отключать цель без удаления
* бот должен проверять membership через Telegram API
* если цель недоступна для проверки, она помечается как невалидная в конфиге

### Ограничение

Бот может проверять подписку только там, где:

* он добавлен,
* у него достаточно прав,
* Telegram позволяет получить статус участника.

---

# 6.2. Ограничение доступа к чату

Если условия не выполнены, бот должен применять один из режимов.

### Режим MVP

**Restrict mode**:

* пользователь может читать чат,
* но не может писать сообщения.

Это базовый и самый адекватный режим.

### Дополнительно, но не обязательно в первой итерации

**Delete-only mode**:

* пользователь технически может писать,
* бот удаляет сообщения постфактум.

Для монетизации хуже, чем restrict mode, поэтому в MVP делать основной режим именно restrict.

---

# 6.3. Уведомление о необходимости подписки

При первом нарушении / входе бот отправляет сервисное сообщение:

Содержимое:

* краткое объяснение, что для общения нужно подписаться;
* список обязательных чатов / каналов;
* кнопки перехода;
* кнопка проверки статуса.

### Требования

* уведомление должно быть кратким;
* без дублей;
* должно автоматически удаляться через заданное время;
* текст должен настраиваться админом хотя бы частично.

### Пример логики текста

“Чтобы писать в этом чате, подпишись на обязательные каналы ниже и нажми ‘Проверить подписку’.”

---

# 6.4. Дедупликация уведомлений

Одна из ключевых фич, и правильно, потому что иначе бот превращается в орущую помойку.

### Задача

Не отправлять пользователю одно и то же уведомление много раз подряд.

### Правила MVP

* для каждого пользователя в каждом основном чате хранится время последнего уведомления;
* если с прошлого уведомления прошло меньше `notification_cooldown`, новое не отправляется;
* по умолчанию cooldown: **5 минут**;
* если пользователь снова нарушает в этот период:

  * сообщение просто удаляется,
  * счётчик нарушений растёт,
  * новое уведомление не шлётся.

### Дополнительно

Можно хранить `active_notice_message_id`, чтобы:

* не создавать новое сообщение,
* а редактировать существующее или просто не плодить сущности.

Для MVP достаточно стратегии: **“не слать повторно в cooldown-окно”**.

---

# 6.5. Мут за спам при неподписке

Если пользователь упрямо пытается писать без выполнения условий, ему должен прилетать мут. Потому что некоторые люди упорны как табуретка, но тупее.

### Логика MVP

Каждое удалённое сообщение неподписанного пользователя считается нарушением.

### Политика по умолчанию

* 1-2 попытки: просто удаление сообщений
* 3 попытки за 60 секунд: мут на 15 минут
* повторный цикл после окончания мута: мут на 1 час
* ещё один повтор: мут на 24 часа

### Требования

* окно подсчёта нарушений должно быть настраиваемым;
* длительности мутов настраиваемые;
* нарушение считается только если причина именно **неподписка**;
* админы и whitelist-пользователи не учитываются.

---

# 6.6. Удаление сообщений спустя время

### Что должно удаляться

1. Сервисные уведомления бота
2. Сообщения нарушителей, если они успели отправиться
3. Технические сообщения об успешной проверке, если такие есть

### Политика MVP

* сообщение нарушителя: удалять **сразу**
* уведомление бота: удалять через **60 секунд**
* сообщение “доступ открыт”: удалять через **15 секунд** или не отправлять вовсе

### Реализация

Нужен планировщик отложенного удаления:

* через Redis TTL / очередь / scheduler
* либо фоновый worker с таблицей задач удаления

---

# 6.7. Кнопка “Проверить подписку”

Обязательная часть MVP.

### Поведение

При нажатии:

1. бот проверяет все обязательные подписки;
2. если все условия выполнены:

   * снимает ограничения;
   * очищает state нарушений при необходимости;
   * может удалить старое уведомление;
3. если не выполнены:

   * показывает, что именно ещё не выполнено;
   * не создаёт новые дублирующие уведомления.

---

# 6.8. Повторная валидация после кеша

Чтобы человек не подписался на 5 секунд, а потом не съебался с каналов сразу обратно.

### MVP-подход

* статус подписки кешируется на короткое время, например **5 минут**;
* после истечения кеша следующая активность пользователя вызывает повторную проверку;
* если обнаружена отписка:

  * доступ снова блокируется;
  * новые сообщения удаляются;
  * может применяться новое уведомление и счётчик нарушений.

Это даёт баланс между нагрузкой на API и полезностью.

---

# 6.9. Исключения

Должны существовать исключения:

* владельцы чата
* администраторы чата
* whitelist пользователей

### MVP

Минимум:

* авто-игнор админов основного чата
* ручной whitelist по user_id

## 7. Команды и управление

Для MVP не надо строить ебаный SAP. Достаточно админ-команд.

## 7.1. Команды администратора

### `/setup`

Инициализация текущего чата как защищаемого.

### `/required_add <chat_id|@username>`

Добавить обязательный канал / чат.

### `/required_remove <chat_id|@username>`

Удалить обязательную цель.

### `/required_list`

Показать список обязательных подписок.

### `/ttl <seconds>`

Установить TTL удаления сервисных сообщений.

### `/cooldown <seconds>`

Установить cooldown дедупликации уведомлений.

### `/mute_policy`

Показать текущую политику мутов.

### `/whitelist_add <user_id>`

Добавить пользователя в whitelist.

### `/whitelist_remove <user_id>`

Удалить из whitelist.

### `/status`

Показать состояние конфигурации:

* бот в чате
* права бота
* список обязательных целей
* валидность целей

### `/stats`

Базовая статистика за период:

* сколько проверок
* сколько блокировок
* сколько снятий ограничений
* сколько сообщений удалено
* сколько мутов выдано

## 8. Нефункциональные требования

## 8.1. Производительность

* система должна выдерживать активный публичный чат с частыми join/message events;
* проверки подписки должны использовать кеш;
* не должно быть лишнего спама Telegram API.

## 8.2. Надёжность

* при временной ошибке Telegram API не должно происходить падение процесса;
* ошибки должны логироваться;
* фоновые задачи удаления не должны ломать основной поток.

## 8.3. Масштабируемость

MVP проектируется так, чтобы потом можно было добавить:

* несколько защищаемых чатов;
* разные наборы обязательных подписок под разные чаты;
* партнёрские ротации;
* A/B тест текстов;
* статистику конверсии по каждому каналу.

## 8.4. Безопасность

* только администраторы защищаемого чата могут менять конфиг;
* команды должны валидироваться по user_id и admin status;
* нельзя дать обычному юзеру вручную снять себе restrict.

---

## 9. Архитектурное решение для MVP

## 9.1. Рекомендуемый стек

С учётом нормальной прагматики, а не “давайте ебанём двадцать сервисов ради кнопки”:

* **Python 3.12**
* **aiogram 3**
* **PostgreSQL** для постоянного хранения
* **Redis** для кеша, дедупликации, rate-limit, TTL
* один бот-процесс + один фоновый worker

### Почему так

* aiogram нормально подходит под Telegram-ботов;
* Redis удобно использовать для cooldown, счётчиков нарушений и отложенных операций;
* PostgreSQL нужен для конфигов, whitelist, статистики, истории.

### RabbitMQ

Для MVP не обязателен. Можно воткнуть позже, если захочется промышленного пафоса. Пока это будет из пушки по мухе.

## 11. Бизнес-логика по событиям

## 11.1. Событие: новый участник вошёл

1. Проверить, является ли пользователь исключением.
2. Проверить подписки.
3. Если не подписан:

   * выдать restrict;
   * отправить уведомление;
   * сохранить state.
4. Если подписан:

   * ничего не делать.

## 11.2. Событие: пользователь отправил сообщение

1. Проверить исключения.
2. Проверить кеш подписки.
3. Если кеш свежий и статус `ok`:

   * пропустить.
4. Если кеш просрочен:

   * перепроверить.
5. Если статус `failed`:

   * удалить сообщение;
   * увеличить счётчик нарушений;
   * при необходимости отправить уведомление;
   * при достижении порога выдать мут.

## 11.3. Событие: нажата кнопка “Проверить подписку”

1. Выполнить повторную проверку.
2. Если `ok`:

   * снять restrict;
   * очистить штрафной state при необходимости;
   * удалить уведомление.
3. Если `failed`:

   * показать, чего не хватает.

## 12. Edge cases

## 12.1. Пользователь не начал диалог с ботом в ЛС

Не проблема. MVP должен работать прямо в чате через inline-кнопки и service flow.

## 12.2. Бот не может проверить target chat

Если бот не имеет доступа к обязательному каналу / чату:

* цель помечается как ошибочная;
* в `/status` это видно;
* такая цель не должна молча ломать всю систему.

## 12.3. Telegram API временно недоступен

* использовать последний известный статус кратковременно;
* логировать ошибку;
* не падать процессом.

## 12.4. Пользователь вышел и вошёл заново

State должен корректно подхватываться, restrictions применяться заново при необходимости.

## 12.5. Пользователь удалил старое уведомление или оно уже пропало

Это не должно ломать дедуп. Дедуп должен жить по времени, а не только по `message_id`.

---

## 13. Метрики MVP

Нужно собирать хотя бы базу, иначе вся эта затея превращается в шаманство.

### Основные метрики

* количество новых участников
* количество участников, не выполнивших условия
* количество успешных валидаций
* конверсия в выполнение условий
* количество удалённых сообщений
* количество выданных мутов
* среднее время от входа до выполнения условий
* эффективность по каждому обязательному каналу / чату

---

## 14. Что НЕ входит в MVP

Чтобы проект не распух в жирную бесполезную свинью на старте:

* полноценная веб-админка
* A/B тестирование текстов
* сложная партнёрская биллинговая система
* анти-рейд аналитика
* ML/антиспам beyond basic
* персонализированные сценарии подписки
* мультиуровневые тарифы для рекламодателей
* графики и отчёты в отдельном кабинете

Это всё потом. Сначала надо сделать одну штуку, которая **реально работает**.

---

## 15. Критерии готовности MVP

MVP считается готовым, если:

1. Можно подключить публичный чат.
2. Можно задать список обязательных подписок.
3. Новый пользователь без подписок не может писать в чат.
4. Его сообщения удаляются при попытке писать в обход.
5. Бот не шлёт дубли уведомлений в пределах cooldown.
6. За повторный спам выдаётся мут.
7. Уведомления автоматически удаляются через TTL.
8. После подписки и нажатия “Проверить” доступ открывается.
9. При отписке после истечения кеша доступ снова может быть отозван.
10. Админ может менять конфиг командами.

## 16. Рекомендованная версия MVP в одном предложении

**Бот-гардеробщик для публичного чата: без обязательных подписок человек может только стоять у входа и ебланить глазами, а не писать.**

## 17. Короткое ТЗ для разработчика в сухом виде

Сделать Telegram-бота для публичного чата, который проверяет подписку пользователя на обязательные каналы/чаты. Если пользователь не подписан, бот ограничивает право писать в основном чате, отправляет одно сервисное уведомление с кнопками подписки и кнопкой повторной проверки, удаляет сообщения нарушителя, считает попытки обхода и выдаёт мут по настраиваемой политике. Повторные уведомления дедуплицируются по cooldown. Сервисные сообщения автоматически удаляются через TTL. Администратор должен иметь возможность настраивать список обязательных целей, cooldown, TTL, mute policy и whitelist через команды. Архитектура MVP: Python + aiogram + PostgreSQL + Redis.

Если хочешь, следующим сообщением дам это же **в формате нормального dev-ТЗ под monolith/DDD**, с модулями, сущностями, use cases, event flow и списком handler'ов под aiogram.
